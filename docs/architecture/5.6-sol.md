# 5.6 Sol 运行架构

## 目标

5.6 Sol 不再把界面、下载状态和桌面能力堆在单个组件或宽 IPC 面上。新结构把产品流程拆成可独立审查的界面模块，并把所有文件系统、网络和系统调用留在 Electron 主进程。

## 分层

```mermaid
flowchart LR
  UI["React 工作台<br/>连接 · 策展 · 下载 · 监控"] --> Hook["useHfWorkbench<br/>页面状态与工作流"]
  Hook --> Bridge["冻结的 appApi<br/>electron/preload.cjs"]
  Bridge --> Gateway["secureHandle<br/>IPC sender + main frame + URL 校验"]
  Gateway --> Policy["securityPolicy<br/>输入 · Endpoint · Token · 路径"]
  Gateway --> API["hfApi<br/>固定 commit 清单"]
  Gateway --> Runner["DownloadRunner<br/>队列 · 续传 · 哈希校验"]
  Gateway --> Storage["storage<br/>限量 · 0600 · 原子 JSON"]
  Gateway --> History["history sync<br/>存在性 · 引用 · 受控删除"]
  Gateway --> Update["release update<br/>固定仓库 · 平台资产 · SHA-256"]
```

### 渲染层

- `src/App.tsx`：只负责工作台编排和区域关系。
- `src/features/hf/hooks/useHfWorkbench.ts`：管理仓库、清单、选择、历史、下载和偏好状态。
- `SourceSetupPanel.tsx`：来源、Token、目录与连接状态。
- `SelectionWorkspace.tsx`：推荐方案、筛选和文件清单。
- `DownloadDock.tsx`：下载前摘要与主操作。
- `StatusPanel.tsx`：运行环境、队列、进度与日志。
- `HistoryPanel.tsx`：历史筛选、恢复与重试。

渲染层没有 Node.js、任意文件读写或任意命令执行能力。

### Preload 桥

`electron/preload.cjs` 只暴露冻结的业务 API。文件打开、文件定位、受控目录、历史同步/删除和更新检查分别使用专用 channel；不会把原始 `ipcRenderer` 暴露给页面。

### 主进程

`electron/main.ts` 负责：

- 单实例锁与主窗口生命周期
- `sandbox`、`contextIsolation`、导航、权限和 CSP
- IPC sender、主 frame 与可信 renderer URL 校验
- 用户批准下载目录的持久化与 realpath 解析
- Token、Endpoint、仓库 ID、下载请求的二次校验
- 下载前重新读取清单和磁盘空间预检
- 历史、偏好和运行目录管理
- 历史与受控下载根的本地文件核对，以及需要显式模式的删除动作
- 固定 GitHub Release 来源、平台资产选择、更新下载与 SHA-256 校验

### 下载核心

下载流程的不可变身份由以下字段共同决定：

```text
Endpoint + owner/repo + commit revision + file path
```

1. 先读取仓库元数据并取得 commit SHA。
2. 使用该 commit 读取 tree，清单项携带 revision 与可用内容哈希。
3. 下载 URL 固定到 commit，不使用可变的 `main`。
4. 输出目录使用 `owner/repo` 两级结构，避免不同所有者的同名仓库冲突。
5. 分片名称绑定完整下载身份，续传还要求强 ETag 匹配。
6. LFS 内容按 SHA-256 校验；普通 Git 文件按 blob OID 校验。
7. 没有可信哈希的既有文件不会仅凭大小被跳过。

## 状态流

```mermaid
stateDiagram-v2
  [*] --> Configure
  Configure --> Manifest: 测试 Endpoint / 读取固定 commit
  Manifest --> Curate: 清单成功
  Curate --> Preflight: 选择文件并开始
  Preflight --> Downloading: 路径、revision、磁盘检查通过
  Preflight --> Curate: 校验失败
  Downloading --> Completed: 长度与内容身份通过
  Downloading --> Failed: 网络、磁盘或哈希失败
  Downloading --> Cancelled: 用户取消
  Failed --> Curate: 恢复或重试
  Cancelled --> Curate: 保留可验证分片
```

## 数据落点

- macOS/Linux：`~/Program/HuggingFace/HF_Model_Downloader`
- 默认下载：`~/Program/Downloads`
- Windows 目录式 portable：`HF_MODEL_DOWNLOADER_PORTABLE_ROOT/HF_Model_Downloader_Data`

macOS/Linux 继续使用当前用户目录下的既有 Sol 数据布局。Windows 发布 ZIP 则把应用数据、默认下载、应用缓存、Chromium 缓存、Electron userData/session、日志、崩溃记录与临时文件都收在解压项目根的 `HF_Model_Downloader_Data/` 下；Electron、DLL、locale 和应用资源位于同级 `HF Model Downloader/` 目录。

Windows 根目录由启动器通过 `HF_MODEL_DOWNLOADER_PORTABLE_ROOT` 显式传入。主进程只采纳绝对、已存在、自身非符号链接、包含便携标记且确实包含当前 EXE 的目录。用户绕过启动器直接打开内部 EXE 时，主进程会验证 ZIP 根的 `.hf-model-downloader-portable-root` 标记；若标记缺失，则以 EXE 所在目录为最小回退边界，不回退到 Windows 用户目录。更新目录同样经过真实路径包含性检查，预先放置的 junction / reparse point 不能把更新包带出项目根。

历史、偏好、缓存、session 和日志分开存放。macOS/Linux 的旧数据迁移只读取历史与偏好白名单，并重写去除 Token 后的偏好；不会递归复制整套旧 Electron userData。Windows 目录式便携版不会自动读取或改写用户配置盘上的旧 Electron 数据，避免首次运行重新触碰 C 盘；需要保留旧记录时应由用户自行从旧版本恢复选择。

## Windows 目录式便携交付

```text
HF-Model-Downloader-5.6.2-windows-x64-portable.zip
├── Start HF Model Downloader.cmd
├── HF Model Downloader/
│   ├── HF Model Downloader.exe
│   ├── resources/app.asar
│   ├── locales/
│   └── Electron DLL / PAK / snapshot files
├── README-Windows.txt
└── .hf-model-downloader-portable-root
```

`HF Model Downloader.exe` 是 Electron 运行目录的一部分，并非安装器。发布资产只有外层 ZIP；构建不再创建 NSIS portable wrapper 或发布顶层 EXE。检查更新仍按版本、平台和架构选择同名 portable ZIP，因此不改变渲染层或 preload 的更新接口。

根目录启动器会在 Electron 原生启动阶段之前创建本地数据目录，并把 `APPDATA`、`LOCALAPPDATA`、`TEMP`、`TMP`、Chromium userData 与磁盘缓存指向 `HF_Model_Downloader_Data/`。如果解压目录只读、便携标记缺失或目录无法创建，启动器会停止而不是回退到系统盘。

## 历史与本地文件同步

历史记录保存下载时的批准根、仓库身份和文件清单。刷新历史只在对应受控下载根中核对文件存在性：

1. 所有记录文件都不存在时，清理该历史记录。
2. 只有部分文件缺失时，保留记录并标记缺失数量，避免把不完整下载误报为完整。
3. “只删记录”不会触碰磁盘文件。
4. “记录与文件一起删除”必须由界面显式确认；主进程重新校验真实路径、根目录与其他历史引用后才逐项删除。
5. 只清理受控根内已为空的仓库目录，不递归删除未知内容。

## 便携更新流

```mermaid
sequenceDiagram
  participant UI as React 更新卡片
  participant Main as Electron 主进程
  participant GH as github.com / api.github.com
  participant Disk as appData/updates
  UI->>Main: checkForUpdates()
  Main->>GH: HTTPS 获取 Yifo98/HF_Model_Downloader Release
  Main-->>UI: 版本、日志、平台资产、大小
  UI->>Main: prepareUpdate()
  Main->>GH: 下载当前 platform/arch 便携 ZIP + SHA256SUMS.txt
  Main->>Disk: 写入临时文件并核对 SHA-256
  Main-->>UI: 已验证 / 失败
  UI->>Main: applyPreparedUpdate()
  Main-->>UI: 揭示或打开已验证资产
```

当前发行没有平台签名，因此更新流不会伪装成静默自替换：应用只下载、校验并揭示当前平台的便携包，由用户退出旧版本后完成替换。

## 关键不变量

- Token 只允许发送到 `https://huggingface.co`。
- 正式包不接受 `VITE_DEV_SERVER_URL`；开发态也只允许 loopback。
- 远端 Endpoint 必须为 HTTPS；HTTP 只允许开发态 loopback。
- 正式打包版只允许官方源和内置 HF Mirror；任意自定义 Endpoint 仅在开发模式开放。
- renderer 不能指定任意系统路径或任意外链。
- 历史刷新与删除不能越出记录绑定的受控下载根；本地删除必须携带显式删除模式。
- 更新只接受 `Yifo98/HF_Model_Downloader` 的 HTTPS Release、当前平台/架构便携资产与同一 Release 的 `SHA256SUMS.txt`。
- Windows 便携根只来自通过校验的启动器环境变量或本地运行目录；运行数据不能静默回退到用户配置盘。
- 单次最多 10,000 个去重后的合法路径，并检测大小写不敏感文件系统冲突。
- 下载前要求已知文件大小，并保留 10% 加 512 MiB 的磁盘安全余量。
- 状态 JSON 有 8 MiB 上限，使用私有权限和原子替换。
