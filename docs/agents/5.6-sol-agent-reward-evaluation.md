## 计量边界

### 什么可以计量

本轮从本机 Codex rollout 的 `token_count` 事件读取以下字段：

- `input_tokens`
- `cached_input_tokens`
- `output_tokens`
- `reasoning_output_tokens`
- `total_tokens`

subagent 在 fork 时会复制父会话的历史计数。为了避免把启动前的整段对话重复算给每个子智能体，本报告采用：

```text
subagent 实际 token = 最后一个 total_token_usage
                    - session_meta 同一秒内最后一个继承基线
```

root 主线采用对应轮次用户请求之前的最后一个计数，减到结算点或明确标注的采样点。`reasoning_output_tokens` 是 output 的子集，不再重复加入总数。

### 什么不能计量

- 无法把共享滚动 rate limit 精确拆到单个智能体。
- 无法从现有日志推导真实货币费用或订阅余额。
- cached input 的额度权重没有在本地日志中公开，因此不能把 42.46M raw tokens 直接解释成同等额度消耗。
- wall time 彼此重叠，因为多个 subagent 并行执行；不能把每行时长相加当作总工时。
- 5.6.2 root 与 `agent_evaluation_analyst` 在采样后仍继续工作，后续 token 不会倒填进本快照。

如果只把“非缓存输入 + 输出”视为最低活动量：

- 5.6.1 为 **2,118,270–42,462,590 tokens**。
- 5.6.2 截至采样为 **2,624,726–42,369,238 tokens**。

区间下界把 cached input 权重视为 0，上界视为 100%；它们是活动量边界，不是价格或订阅额度区间。

## Agency Agents 的参与真相

[Agency Agents 官方仓库](https://github.com/msitarzewski/agency-agents)把各角色描述为带有明确工作流、交付物与成功指标的专业 profile，并说明 Codex 需要先把 profile 转换、安装到 `~/.codex/agents/`，再按名称引用。

两个轮次都没有发生这个 profile 激活流程。证据是：

- 所有被核查会话的 `source.subagent.thread_spawn.agent_path` 都是自定义 task name，包括 depth 2 的 nested reviewer。
- 所有被核查会话的 `agent_role` 都是 `null`。
- task name 与本地 TOML 的正式 `name` / `filename` 不一致。
- root 使用的是 `collaboration.spawn_agent` 的自定义消息合同；即使任务名语义相近，也不能据此声称加载了 Agency profile。

因此，下面只能做“能力匹配建议”，不能把 5.6.1 的分数追溯给 Agency profile。

| 实际 task | 最接近的 Agency 能力 | 是否真实实例化 profile |
| --- | --- | --- |
| `sol_ui_followup` | Frontend Developer + UX Architect | 否 |
| `runtime_file_sync` | Desktop App Engineer + Workflow Architect | 否 |
| `portable_release_engineer` | Desktop App Engineer + Git Workflow Master | 否 |
| `application_security_reviewer` | Application Security Engineer | 否 |
| root 主线 | Agents Orchestrator 的协调职责 | 否 |

5.6.2 同样如此：`windows_portable_562`、`windows_portable_review`、`icon_imagegen_worker`、`agent_evaluation_analyst`、`portable_security_reviewer_562` 全部是 task-scoped collaboration agent，不是 Agency profile 实例。

### 官方与本机目录快照

- [官方 GitHub tree API](https://api.github.com/repos/msitarzewski/agency-agents/git/trees/main?recursive=1)：按 `^[^/]+/[^/]+\.md$` 且排除 `examples/` 的约定两级路径口径，采样为 **244** 个 Markdown 条目。
- 本机 `~/.codex/agents/*.toml`：采样为 **254** 个 TOML。

244 与 254 都是文件快照，不是“可同时有效工作的 244/254 人团队”。两级路径口径会漏掉更深层的游戏引擎角色，也可能把目录说明类 Markdown 算入；本机 TOML 则是转换后的本地 catalog。角色越多不代表当前任务越强，反而会增加路由、上下文和职责重叠成本。

## 下一轮调度预算

目标：把单轮 raw token 从约 42M 降到 **8M–12M**，同时不削弱真实验证。5.6.2 仍达到 42.37M；这份预算是在智能体已经启动后形成，不能倒算为当轮违规，但下一轮必须在 spawn 前生效。

| 工作流 | 建议角色 | Raw token 预算 | 停止条件 |
| --- | --- | ---: | --- |
| 图标与 GitHub 品牌卡 | UI Designer / image worker | 0.8M–1.2M | PNG、ICNS、ICO、Dock、README 暗色背景均通过 |
| Windows ZIP-only 与目录便携化 | Desktop App Engineer | 1.2M–2.0M | ZIP 内启动器、项目内 data/cache/deps、无独立 Release EXE |
| 安全 + 最终证据 | AppSec + Evidence Collector，可串行 | 1.0M–1.8M | 删除/更新安全回归 + 最终 ZIP/图标证据齐全 |
| root 集成、回归、GitHub | root | 5M–7M | 完整检查、真机边界披露、Release 资产一致 |

执行规则：

1. subagent 默认使用短 fork，只传最近需求、写入范围、接口合同和必要文件；不要复制整条历史会话。
2. 每个写入 agent 最多拥有一个高耦合目录，避免主线反复解冲突。
3. 纯只读 reviewer 在实现稳定后再启动，不与写入 agent 同步扫描半成品。
4. 达到预算 80% 时先提交“已证实事实、剩余风险、待验证清单”，由 root 决定是否追加。
5. Release gate 必须同时满足：自动检查、真实应用/目标平台证据、最终资产清单、用户数据排除、用户验收合同。
